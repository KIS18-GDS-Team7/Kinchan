# コーディング規約 (frontend)

Kinchan の frontend コードの書き方と、frontend の変更で守る作業手順を定める。

## 作業を始める前

- ブランチと PR の運用は [AGENTS.md](../../AGENTS.md) の「ブランチと PR」に従う。

## コードの変更

- 必要な修正箇所以外のファイルとコードを変更しない。既存の書き方、命名、構成を優先し、無関係なリファクタリングや整形を行わない。
- 型は作業開始時から明示し、未完成でも値、引数、戻り値、画面の状態遷移がコード上で追える状態にする。
- コードから読み取れない理由だけをコメントにする。処理内容を説明するコメントや、将来削除することを前提としたコメントアウトしたコードは残さない。
- TODO を残す場合は対応する Issue 番号を付ける。
- 識別子は英語で書き、ローマ字と日本語の識別子は使わない。コメントと docstring は日本語で書く。
- 用語集 (`docs/requirements/requirements.md` の 4 章) の語を識別子にするときの英語表記は TBD。同じ語に複数の英語表記が混在すると、検索で漏れが出るため、用語集で 1 つに決める。
- 用語集 (`docs/requirements/requirements.md` の 4 章) にない語を新たに持ち込まない。未定義の語は、画面名や機能名を確定するまで TBD とする。
- コードとドキュメントで同じ機能名を使う。画面の構成やボタン配置は画面設計で扱い、要件定義書に画面構成を書かない。
- 設計判断をした場合は ADR を追加する。形式は `docs/ADR/0001-record-ADR.md` に従い、見出しは `# タイトル` `## ステータス` `## 背景` `## 決定` の 4 つだけとする。

## テスト

- 完了条件は、設計段階で定めた挙動について単体テストが合格することとする。テスト対象には正常系、入力値の境界、エラー処理、権限、画面の状態遷移を含める。
- 結合テストが合格し、API の入出力、画面遷移、共通レイアウト、認証済み・未認証の状態で既存コードとの互換性を満たすことを完了条件とする。
- 設計段階で定めた排他処理などの並行実行時の挙動も、該当するテストが合格することを完了条件に含める。
- テストで検証できない表示や操作上の要件は、ブラウザで想定した表示と状態遷移が得られることを完了条件とする。
- テストツール、テストの書き方、カバレッジの基準は TBD。決定後はこの文書を更新する。

## コミットと PR

- コミットメッセージは日本語で、1 行目に何をしたかを書く。
- PR 本文は `.github/pull_request_template.md` に従う。
- 自分の PR は承認できない。承認や再レビューが必要な場合は、メンバーに依頼する。
- `main` と `dev/**` への PR は、作者以外の承認が 1 件以上必要。
- `frontend/**` を変更する PR では frontend チームの承認が必要。
- 複数チームの管轄に触れる場合は、PR の概要にその旨を書く。承認後に push すると承認が無効になるため、再度レビューを依頼する。
- `docs/` の変更内容は、システムの動作で書く ADR-0002 と、定義済みの語だけを使う ADR-0003 に適合させる。
- 設計判断を含む場合は ADR を追加する。

## 触らないもの

- `.github/rulesets/`、`.github/CODEOWNERS`、`.github/workflows/` は変更しない。変更が必要な場合は提案に留め、platform チームのレビューを受ける。
- `review/*`、`approved/*` タグと GitHub Release は変更しない。
- `.asta`、`.png` などのバイナリは手で編集しない。
- AGENTS.md、CONTRIBUTING.md はこの規約のために変更しない。
