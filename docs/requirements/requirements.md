## 1. 目的・背景

### 1.1 本システム(Kinchan)が解決する課題

- 法律では勤怠を1分単位で記録することが義務付けられているが、現状15分単位など実施していない店舗が存在する
- 出勤時・退勤時の打刻忘れや誤入力が発生し、勤怠管理者の修正業務など手間が発生している
- アナログで勤怠を登録しているため、手作業による時間や記入ミス・確認ミスのリスクがある
- 労働時間や残業状況が可視化されず、36協定の労働時間超過や過重労働のリスクがある

### 1.2 目的

- 法律に基づいた1分単位の勤怠の打刻・記録が行えるシステムの構築
- 希望シフトの提出から勤怠集計までの一連の業務をシステムで行い、手作業による転記・集計の負担を解消すること
- リアルタイムでの勤務実態の可視化と、管理業務の効率化

### 1.3 ゴール

- 1分単位で打刻、及び勤怠実態をシステムで一括管理できる状態にすること
- 従業員のシフト希望提出・変更申請、勤怠管理者の承認・シフト管理をシステム上で完結できる状態にすること
- 打刻データ・確定シフトに基づき、手作業なしで予定シフトと実際の勤務状況を表示して確認できる状態にすること

## 3. ステークホルダー・アクター

| アクター | 説明 |
| --- | --- |
| 従業員 | クライアント企業のユーザー。すべてのユーザーは所属単位の従業員として振る舞い、打刻・申請・シフト希望の送信を行う |
| マスタ管理者 | マスタ管理者権限を持つユーザー(クライアント企業に最低一人は存在する)。ユーザー・権限・所属単位・管理先の登録や設定を行い、操作は所属単位に縛られない |
| 勤怠管理者 | 勤怠管理者権限を持つユーザー。管理先の所属単位(複数可)の従業員のシフト・勤怠・申請を扱う |

- 権限としての「従業員」は無い。マスタ管理者・勤怠管理者はユーザーに付加する権限で、どちらも従業員としても振る舞う(#83)
- 店舗・支店・事業部といった単位は「所属単位」と呼ぶ。入れ子にしない。従業員としての所属は 1 つ、勤怠管理者の管理先は 1 つ以上(#84)
- 「マスタ管理者」は旧「システム管理者」(#83)。システム全体の管理者と紛れるため、マスタデータ(ユーザー・権限・所属単位)の管理者であることが伝わる語に改名(#113)
