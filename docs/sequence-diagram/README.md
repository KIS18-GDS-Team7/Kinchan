# シーケンス図

ユースケース記述 (`docs/usecase/`) の各 UC を 1 枚ずつシーケンス図にしたもの。#42 の成果物。図はテキストの定義から SVG を直接書き出して作る。描き方の決まりは [ADR-0034](../ADR/0034-sequence-diagram-rules.md) に記録している。

- `src/UC-xxx.txt`: 図の定義 (1 行 1 メッセージ)。図を直すときはこれを直す
- `images/UC-xxx.svg`: `seqsvg.py` で書き出した図。手で編集しない
- `seqsvg.py`: 定義から SVG を書き出すスクリプト

SVG の文字は `<text>` 要素のまま出力するので、検索・diff・自動レビューで読める。

担当: @Luka-Jr2

## 使い方

```sh
cd docs/sequence-diagram
python3 seqsvg.py                 # src/ の全ファイルを images/ に書き出す
python3 seqsvg.py src/UC-302.txt  # 1 ファイルだけ書き出す
```

Python 3 の標準ライブラリだけで動く。`src/` を直したら、書き出した `images/` も同じコミットに入れる。

## 定義の書式

```text
title UC-302 ログアウトする           # 図の名前
scope メインフロー、Ex-1               # 右上のノートに出す、この図で描いたフロー

actor A 従業員                         # ライフライン: 種類 ID 名前
boundary H 従業員ホーム画面             # 種類は actor / boundary / control / participant / entity
control C ログイン制御                  # 左から書いた順に並ぶ

A -> H : ログアウトボタンを押す          # メッセージ (番号は自動で振る)
C --> H : 戻り値                        # 戻りメッセージ (破線、番号なし)
C -> C : ログアウトした状態にする        # 自己メッセージ
note : 出典など                         # 直前のメッセージ (または直前の end の断片) に付くノート

break ガード条件                        # break / opt / loop / alt
  ...
end
alt 保存に失敗した
  ...
else 保存に成功した                     # alt の 2 つめ以降の区画
  ...
end
# から始まる行はコメント
```

## 描き方

- **ライフライン**: 左から アクター / 画面 (Boundary) / 制御 (Control) / DataManager / エンティティ の順に並べる。画面の名前は画面遷移図、エンティティの名前は概念クラス図に合わせる。
- **DataManager**: DB アクセスをカプセル化するラッパー。制御はエンティティに直接アクセスせず、DataManager に取得・保存を頼む。DataManager がエンティティに対して同じ操作をし、戻り値は DataManager を通って制御に返る。BCE のどれにも当たらないので、四角のアイコン (`participant`) で描く。エンティティにアクセスしない図 (UC-302) には置かない。
- **メッセージ**: UC のメインフローの 1 ステップを 1〜2 本のメッセージにする。戻りメッセージ (破線) は、データを受け取るところだけに書く。アクターの指示は、何を指示するのかが分かる文言にする (「ユーザー情報の変更を指示する」)。
- **アクターへの提示**: 制御 → 画面「〜を渡す」、画面 → アクター「〜を提示する」の 2 本で表す。表示するのは画面で、制御は画面にデータを渡すだけなので、制御 → 画面は「〜を表示する」としない。成功・失敗・キャンセルの完了も同じ形にする。
- **提示する内容**: 画面 → アクターは、何を提示するかを「〜を提示し、〜を求める」の形で書く。提示する前に、制御が DataManager から取得するメッセージを書く。
- **キャンセル**: 画面 → 制御「キャンセルを要求する」、制御 → 画面「キャンセルの完了を渡す」、画面 → アクター「キャンセルが完了したことを提示する」とする。
- **代替フロー・例外フロー**
  - UC を終了・中断するもの、他の UC に戻るもの: `break`。break は最上位に置く (UML の break は、それを囲む断片だけを抜けるため)。
  - 入力のやり直し (元のステップに戻るもの): 戻り先から検証までを `loop` で囲み、中に `opt [誤りがある]`。
  - 保存の失敗で戻るもの: `alt [保存に失敗した]` / `[保存に成功した]` の 2 区画。通知と完了の提示は成功側に入れる。
  - 条件つきで実行されるステップ: `opt`。ノートだけで済ませない。
  - 日ごと・人ごと・申請ごとに繰り返すステップ: `loop`。
- **順序**: 検証と判定は UC のステップの順に並べる。メインフロー n の検証で失敗したら、n+1 の処理を通らずに break する。
- **画面**: 1 本目のメッセージは、画面遷移図でそのボタンがある画面に送る。結果は遷移先の画面から提示する。入力確認ダイアログは独立したライフラインにする。
- **権限**: 従業員が持つ権限のリスト (マスタ管理者権限・勤怠管理者権限) として扱い、権限のライフラインは置かない (UC-104・107・109)。
- **ノート**: 判断の出典 (備考・ADR・Issue 番号) と、UC の事後条件から決まること (まとめて保存する、など) を書く。画面遷移図・概念クラス図にない名前を使うときは「暫定」と書く。
- **別図**: 代替フローが 10 ステップ以上の別経路になる場合は別の図にし、本編のノートから参照する (UC-306・UC-307 の Alt-1)。

## 描き方から外れた所

UC のステップの順序を守るため、次の図は上の描き方から外れている。ノートに理由を書いてある。

- UC-206・209・214・307-alt1: 戻り先と検証の間にキャンセル (Ex-1) がある、または戻り先がキャンセルより前にある。そのため、loop ではなく alt の入れ子で描いた
- UC-307: Alt-4 (下書きを保存して終了) の break の中に、保存に失敗したら MF5 に戻る経路がある

## レビューの指摘への対応

PR #125 に付いたコメントは、UC 記述 (origin/main) と照らして正しいかを確かめてから反映した。

| UC | コメント | 対応 |
| --- | --- | --- |
| UC-102 | 「変更を指示する」は何の変更か | 「ユーザー情報の変更を指示する」にした |
| UC-102 | 更新の後に取得し直して画面を更新していない | UC-102 の MF10 は完了の提示だけなので、更新後の取得は描かない。MF4 の前に対象のユーザーを取得する抜けを直した |
| UC-103 | MF2・MF4 の扱いが違う | 制御が表示した内容 (ユーザーの一覧、削除の確認内容) を、画面がアクターに提示していなかった。「〜を提示し、〜を求める」にした |
| UC-105 | 登録されている所属単位を提示するのが正しい | UC の MF4 どおりにした |
| UC-106 | 現在の所属と所属単位をそれぞれ提示するのが正しい | UC の MF4 どおりにした |
| UC-205 | MF1〜2 の間でシフト希望を取得していない | 内容を提示する前に、シフト希望を取得するようにした |
| UC-109 | 勤怠管理者権限の取得 (#8〜10) はいらない | 権限はユーザーの一覧と一緒に取得し、個別の取得をなくした。UC-109 の Alt-1 があるため、判定と提示は残した |

## 未決の点

- 画面遷移図にない画面・ボタン、概念クラス図にない属性 (勤務ステータス、削除済み、操作者・修正者・根拠、権限のリスト など) と DataManager は、各図のノートに「暫定」と書いた。画面遷移図・概念クラス図とどちらに合わせるかは #42 で相談する。
- DataManager は 1 つで全エンティティを受け持っている。エンティティごとに分けるかは未定。
- 活性区間 (ライフライン上の細長い四角) は描いていない。
