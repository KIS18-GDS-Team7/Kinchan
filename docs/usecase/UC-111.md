# UC-111 ユーザーの所属を編集する

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | ユーザーの所属を編集する(UC-111) |
| 目的 | アクターが所属が設定済みのユーザーの所属を別の所属単位に変更し、そのユーザーが変更後の所属単位の従業員として振る舞える状態にする |
| アクター | システム管理者 |
| 開始条件 | アクターがユーザーの所属の変更を要求する |
| 事前条件 | ・アクターがログインしていること(UC-001)<br>・アクターがシステム管理者権限を持つこと<br>・対象のユーザーが登録されていること(UC-103)<br>・対象のユーザーが削除済みでないこと<br>・変更後の所属とする所属単位が登録されていること(UC-117) |
| 事後条件 | ・対象のユーザーの所属が指定された所属単位に更新されていること<br>・対象のユーザーの既存のシフト・申請が変更されていないこと<br>・対象のユーザーの既存の勤怠記録が修正されていないこと |
| 拡張点 | なし |
| 関連ユースケース | ・ユーザーの所属を設定する(UC-110)<br>・所属単位を登録する(UC-117)<br>・ユーザー一覧を表示する(UC-116) |

## イベントフロー

### メインフロー

1. アクターはシステムにユーザーの所属の変更を要求する
2. システムはアクターに対象のユーザーの指定を求める
3. アクターはシステムに対象のユーザーを指定する
4. システムはアクターに対象のユーザーの現在の所属と登録されている所属単位を提示し、変更後の所属とする所属単位の指定を求める
5. アクターはシステムに変更後の所属とする所属単位を1つ指定する
6. システムはアクターに対象のユーザーの変更前と変更後の所属を提示し、変更の確認を求める
7. アクターはシステムに変更を指示する
8. システムは対象のユーザーの所属を指定された所属単位に更新する
9. システムはアクターに所属の変更が完了したことを提示する

### 代替フロー

#### Alt-1: メインフロー4で、対象のユーザーの所属が設定されていなかった場合

1. システムは対象のユーザーの所属が設定されていないことをアクターに提示する
2. このユースケースを終了する

### 例外フロー

#### Ex-1: メインフロー7より前にアクターが変更のキャンセルを要求した場合

1. アクターはシステムに変更のキャンセルを要求する
2. システムは入力された内容を破棄する
3. システムはアクターにキャンセルが完了したことを提示する
4. システムは待機状態に戻る

事後条件

- 入力された内容が破棄されていること
- 対象のユーザーの所属が変更されていないこと
- システムが待機状態に戻っていること

#### Ex-2: システムがユーザーの保存に失敗した場合

1. システムはアクターに保存に失敗したことを提示する
2. システムは入力された内容を保持したまま、メインフロー6に戻る

事後条件

- 対象のユーザーの所属が変更されていないこと

## 備考

1. 所属は登録されている所属単位から1つ指定する。1ユーザーにつき所属は1つ(2026-10-21の会話)
2. 所属を変更しても、対象のユーザーの既存のシフト・申請は変更せず、既存の勤怠記録は修正しない。変更後は、変更後の所属単位を管理先に持つ勤怠管理者が対象のユーザーの勤怠・シフト・申請を扱う(A-24を所属単位に読み替え)
3. 所属が設定済みのユーザーが対象。所属が未設定のユーザーの所属はユーザーの所属を設定する(UC-110)で設定する(A-21)
4. 所属が未設定のユーザーは、シフト・打刻・シフト希望・申請を扱う従業員のユースケースを実行できない(暫定)
5. このユースケースで所属を変更した後、および対象期間を変更・削除した後の、既存のシフトと「未処理」のシフト希望・シフト日時変更申請(変更前の対象期間に含まれる日を対象とするもの)の扱いはTBD(要起票)。対象になる操作は、シフトを公開する(UC-218)での下書きの公開、シフトを一覧表示する(UC-308)での提示、シフト希望を承認する(UC-207)・シフト日時変更申請を承認する(UC-215)での承認。対象期間の変更・削除はシフト希望の対象期間・受付期間を登録する(UC-217)でTBD
6. UC名は暫定名。requirements.mdでは「ユーザーの所属店舗を編集する」。改名は別途。フロー本文では「変更する」と書く
7. requirements.mdではアクターは「管理者」。本書ではシステム管理者と書く(#83)。改名は別途
