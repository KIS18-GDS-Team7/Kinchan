# UC-212 勤怠を修正する

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | 勤怠を修正する(UC-212) |
| 目的 | アクターが従業員からの申請によらず、管理先の従業員の勤怠記録を直接修正できる状態にする |
| アクター | 勤怠管理者 |
| 開始条件 | アクターが勤怠の修正を要求する |
| 事前条件 | ・アクターがログインしていること(UC-001)<br>・アクターが勤怠管理者権限を持つこと<br>・アクターに管理先が割り当てられていること(UC-118)<br>・対象の従業員が管理先の従業員であること |
| 事後条件 | ・勤怠記録が修正後の打刻の一覧に更新されていること<br>・修正前の勤怠記録、修正者、修正日時、修正理由、根拠が修正履歴として記録されていること<br>・(対象の従業員が削除済みユーザーでなければ)対象の従業員に勤怠記録が修正されたことが通知されていること |
| 拡張点 | なし |
| 関連ユースケース | ・勤怠修正申請を一覧表示する(UC-209)<br>・勤怠修正申請を承認する(UC-210)<br>・勤怠記録を一覧表示する(UC-313) |

## イベントフロー

### メインフロー

1. アクターはシステムに勤怠の修正を要求する
2. システムはアクターに対象の従業員(管理先の従業員)と対象日の指定を求める
3. アクターはシステムに対象の従業員と対象日を指定する
4. システムはアクターに対象日の勤怠記録(打刻の一覧: 種類・打刻日時)と修正履歴を提示し、修正後の打刻の一覧と修正理由の入力を求める
5. アクターはシステムに修正後の打刻の一覧と修正理由を入力する
6. システムは入力された修正後の打刻の一覧と修正理由を検証する
7. システムはアクターに修正前と修正後の勤怠記録を提示し、修正の確認を求める
8. アクターはシステムに修正を指示する
9. システムは修正前の勤怠記録、修正者、修正日時、修正理由、根拠を修正履歴として記録する
10. システムは勤怠記録を修正後の打刻の一覧に更新する
11. システムは、対象の従業員が削除済みユーザーでなければ、対象の従業員に勤怠記録が修正されたことを通知する
12. システムはアクターに修正が完了したことを提示する

### 代替フロー

#### Alt-1: メインフロー4で、対象日に勤怠記録が無かった場合

1. システムは対象日に勤怠記録が無いことをアクターに提示し、勤怠記録を新しく登録することの確認を求める
2. アクターはシステムに勤怠記録の登録を指示する
3. システムはアクターに修正後の打刻の一覧と修正理由の入力を求める
4. メインフロー5に進む

#### Alt-2: メインフロー4で、対象日に「未処理」の勤怠修正申請があった場合

1. システムは対象日に「未処理」の勤怠修正申請があることと、その申請の内容をアクターに提示する
2. メインフロー5に進む

#### Alt-3: メインフロー6で、入力された修正後の打刻の一覧が整合していなかった場合

1. システムは入力された修正後の打刻の一覧に誤りがあることをアクターに提示する
2. メインフロー4に戻る

#### Alt-4: メインフロー6で、修正理由が入力されていなかった場合

1. システムは修正理由の入力が必要であることをアクターに提示する
2. メインフロー4に戻る

#### Alt-5: メインフロー4で、対象の勤怠記録がアクター自身の勤怠記録だった場合

1. システムは対象がアクター自身の勤怠記録であることをアクターに提示する
2. メインフロー5に進む

### 例外フロー

#### Ex-1: メインフロー8より前にアクターが修正のキャンセルを要求した場合

1. アクターはシステムに修正のキャンセルを要求する
2. システムは入力された内容を破棄する
3. システムはアクターにキャンセルが完了したことを提示する
4. システムは待機状態に戻る

事後条件

- 入力された内容が破棄されていること
- 勤怠記録が修正されていないこと
- システムが待機状態に戻っていること

#### Ex-2: システムが勤怠記録の保存に失敗した場合

1. システムはアクターに保存に失敗したことを提示する
2. システムは入力された内容を保持したまま、メインフロー7に戻る

事後条件

- 修正履歴が記録されていないこと
- 勤怠記録が修正されていないこと

## 備考

1. 修正理由は必須とする。修正履歴は削除できない(ドラフトUC-212、A-54)。修正履歴の根拠は「勤怠管理者の直接修正」として記録し、修正履歴の修正理由には入力された修正理由を記録する(暫定)
2. 修正の対象は対象日の打刻の一覧(種類・打刻日時)である。休憩は打刻で記録するため、修正できる打刻の種類は「出勤」「退勤」「休憩開始」「休憩終了」であり、休憩時間は打刻から計算する(#78からの導出、暫定)
3. 修正後の打刻の一覧が整合しているとは、打刻の種類が「出勤」、「休憩開始」と「休憩終了」の組(0回以上)、「退勤」の順に並び、打刻日時が昇順であることをいう。同じ日に2回以上の勤務があってよい(#78)
4. 打刻日時は秒まで記録し、秒まで提示する(#74、A-59)
5. この修正に期限は無い。従業員の修正申請の期限(#85)を過ぎた日の勤怠記録も修正できる
6. 対象日に「未処理」の勤怠修正申請がある場合(Alt-2)、その申請は「未処理」のまま残る。後から勤怠修正申請を承認する(UC-210)でその申請を承認すると、申請内容で上書きされる(#93、A-84)
7. 対象日に勤怠記録が無い場合(Alt-1)は、修正前の勤怠記録が無いことを修正履歴に記録し、メインフロー10で勤怠記録を新しく登録する
8. アクターの所属がアクターの管理先に含まれる場合、アクター自身の勤怠記録を修正できる(Alt-5、A-55)
9. 削除済みユーザーには通知しない(#86、A-19からの導出、暫定)
10. 修正理由の文字数の上限はTBD(要起票)
11. 対象日に当日より後の日を指定できるかはTBD(要起票)
12. 対象日が当日で、対象の従業員の勤務ステータスが「退勤中」でない場合の扱いはTBD(要起票)
13. 対象の従業員に削除済みユーザーを指定できるかはTBD(要起票)
14. 修正履歴はこのユースケースと従業員側の勤怠記録を一覧表示する(UC-313)で提示する(A-54、暫定)
