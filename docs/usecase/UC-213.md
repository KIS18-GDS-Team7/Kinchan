# UC-213 シフト日時変更申請を承認する

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | シフト日時変更申請を承認する(UC-213) |
| 目的 | アクターが「未処理」のシフト日時変更申請を承認し、変更後の日時をシフトに反映できる状態にする |
| アクター | 勤怠管理者 |
| 開始条件 | アクターがシフト日時変更申請を一覧表示する(UC-212)で「未処理」のシフト日時変更申請を指定して承認を要求する |
| 事前条件 | ・アクターがログインしていること(UC-301)<br>・アクターが勤怠管理者権限を持つこと<br>・アクターに管理先が割り当てられていること(UC-109)<br>・対象の従業員が管理先の従業員であること<br>・対象のシフト日時変更申請の処理状態が「未処理」であること |
| 事後条件 | ・シフト日時変更申請の処理状態が「承認済」になっていること<br>・変更前のシフトの内容、操作者、操作日時が変更履歴として記録されていること<br>・シフトが変更後の勤務日・開始時刻・終了時刻に更新されていること<br>・(申請した従業員が削除済みユーザーでなければ)申請した従業員に承認結果が通知されていること |
| 拡張点 | なし |
| 関連ユースケース | ・シフト日時変更申請を一覧表示する(UC-212)<br>・シフトを変更する(UC-202)<br>・シフト希望の対象期間・受付期間を登録する(UC-215)<br>・シフト日時変更申請内容を一覧表示する(UC-318)<br>・シフトを一覧表示する(UC-308) |

## イベントフロー

### メインフロー

1. アクターはシステムにシフト日時変更申請の承認を要求する
2. システムはアクターに承認するシフト日時変更申請の内容を提示し、承認の確認を求める
3. アクターはシステムに承認を指示する
4. システムは対象のシフト日時変更申請の処理状態が「未処理」であること、変更前のシフトが勤務済み・削除済みでないことを検証する
5. システムは変更後の勤務日が当日以降で、対象の従業員の所属に登録された対象期間に含まれることを検証する
6. システムは変更後の日時が同じ従業員の他のシフトと重複するかを判定する
7. システムはシフト日時変更申請の処理状態を「承認済」に更新する
8. システムは変更前のシフトの内容、操作者、操作日時を変更履歴として記録する
9. システムはシフトを変更後の勤務日・開始時刻・終了時刻に更新する
10. システムは、申請した従業員が削除済みユーザーでなければ、申請した従業員に承認結果を通知する
11. システムはアクターに承認が完了したことを提示する

### 代替フロー

#### Alt-1: メインフロー6で、変更後の日時が登録済みのシフトと重複していた場合

1. システムは重複しているシフトをアクターに提示する
2. システムはそのシフト日時変更申請を承認できないことをアクターに提示する
3. シフト日時変更申請を一覧表示する(UC-212)に戻る

#### Alt-2: メインフロー4で、変更前のシフトが勤務済み、または削除済みだった場合

1. システムは変更前のシフトが変更できない状態であるため承認できないことをアクターに提示する
2. シフト日時変更申請を一覧表示する(UC-212)に戻る

#### Alt-3: メインフロー4で、対象のシフト日時変更申請の処理状態が「未処理」でなくなっていた場合

1. システムは対象のシフト日時変更申請が承認できない状態であることをアクターに提示する
2. シフト日時変更申請を一覧表示する(UC-212)に戻る

#### Alt-4: メインフロー2で、対象のシフト日時変更申請がアクター自身のシフト日時変更申請だった場合

1. システムは対象がアクター自身のシフト日時変更申請であることをアクターに提示する
2. メインフロー3に進む

#### Alt-5: メインフロー5で、変更後の勤務日が当日より前だった場合

1. システムは変更後の勤務日が当日より前であるため承認できないことをアクターに提示する
2. シフト日時変更申請を一覧表示する(UC-212)に戻る

#### Alt-6: メインフロー5で、変更後の勤務日が対象の従業員の所属に登録された対象期間に含まれなかった場合

1. システムは変更後の勤務日が対象期間に含まれないことをアクターに提示する
2. システムはそのシフト日時変更申請を承認できないことをアクターに提示する
3. シフト日時変更申請を一覧表示する(UC-212)に戻る

### 例外フロー

#### Ex-1: メインフロー3より前にアクターが承認のキャンセルを要求した場合

1. アクターはシステムに承認のキャンセルを要求する
2. システムはアクターにキャンセルが完了したことを提示する
3. システムは待機状態に戻る

事後条件

- シフト日時変更申請の処理状態が変更されていないこと
- シフトが変更されていないこと
- システムが待機状態に戻っていること

#### Ex-2: システムがシフト日時変更申請またはシフトの保存に失敗した場合

1. システムはアクターに保存に失敗したことを提示する
2. メインフロー2に戻る

事後条件

- シフト日時変更申請の処理状態が変更されていないこと
- 変更履歴が記録されていないこと
- シフトが変更されていないこと

## 備考

1. 承認時にアクターが変更後の日時を調整するステップは設けない(#91からの導出、暫定)。調整が必要な場合は、シフト日時変更申請を却下する(UC-214)か、シフトを変更する(UC-202)で変更する
2. 変更後のシフトの状態は「公開」のまま変えない(#87の再起票)。変更履歴は削除できない
3. 承認結果の通知はシフトが変更されたことの通知を兼ねる。シフトを変更する(UC-202)の通知は別に出さない
4. 重複は時刻の重なりで判定する(A-33)。重複がある場合は承認せず、申請は「未処理」のまま残る(Alt-1)
5. 勤務済みのシフトとは、シフトの終了日時(勤務日+終了時刻。日をまたぐ場合は翌日)を現在時刻が過ぎていることをいう(暫定)。変更前のシフトが勤務中であっても承認できる(シフトを変更する(UC-202)と同じ扱い、暫定)
6. 変更後の勤務日が当日より前の場合は承認せず、申請は「未処理」のまま残る(Alt-5。A-77からの導出、暫定)
7. 変更後の勤務日は、シフト希望の対象期間・受付期間を登録する(UC-215)で対象の従業員の所属に登録された対象期間に含まれる日に限る(2026-10-22の会話)。含まれない場合は承認せず、申請は「未処理」のまま残る(Alt-6)
8. シフト日時変更申請を送信する(UC-309)の対象は、従業員自身の公開済みで勤務日が翌日以降のシフトである(A-36)
9. 削除済みユーザーの「未処理」のシフト日時変更申請も処理できる(#86、A-19)。ユーザーの削除時に勤務日が翌日以降のシフトは削除されるため、変更前のシフトが削除済みであればAlt-2となる。削除済みユーザーには通知しない(#86、A-19からの導出、暫定)。削除済みユーザーの当日のシフトについてのシフト日時変更申請を承認して、勤務日が翌日以降のシフトになる場合の扱いはTBD(要起票)
10. アクターの所属がアクターの管理先に含まれる場合、アクター自身のシフト日時変更申請を承認できる(Alt-4、A-55)
11. Alt-3は、一覧を提示した後に、他の勤怠管理者が承認・却下した、または従業員が取り下げた場合に当たる。取り下げは従業員がシフト日時変更申請を取り下げる(UC-316)で行う
12. シフトを変更する(UC-202)で、「未処理」のシフト日時変更申請があるシフトを変更した場合の扱いはTBD(要起票)
13. ユーザーの所属を編集する(UC-106)で所属を変更した後、および対象期間を変更・削除した後の、既存のシフトと「未処理」のシフト希望・シフト日時変更申請(変更前の対象期間に含まれる日を対象とするもの)の扱いはTBD(要起票)。対象になる操作は、シフトを公開する(UC-216)での下書きの公開、シフトを一覧表示する(UC-308)での提示、シフト希望を承認する(UC-205)・このユースケースでの承認。対象期間の変更・削除はシフト希望の対象期間・受付期間を登録する(UC-215)でTBD
14. 承認結果は従業員側のシフト日時変更申請内容を一覧表示する(UC-318)で提示される。変更後のシフトは従業員側のシフトを一覧表示する(UC-308)で提示される
