# UC-317 通知を表示する

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | 通知を表示する(UC-317) |
| 目的 | アクターがアクター自身宛ての通知と、その通知に関連する対象を表示できる状態にする |
| アクター | 従業員、勤怠管理者 |
| 開始条件 | アクターが通知の表示を要求する |
| 事前条件 | ・アクターがログインしていること(UC-301) |
| 事後条件 | ・アクターにアクター宛ての通知が提示されていること |
| 拡張点 | なし |
| 関連ユースケース | ・シフトを一覧表示する(UC-308)<br>・シフト希望を一覧表示する(UC-311)<br>・シフト日時変更申請内容を一覧表示する(UC-318)<br>・勤怠修正申請内容を一覧表示する(UC-310)<br>・勤怠記録を一覧表示する(UC-313)<br>・シフト希望を一覧表示する(UC-204)<br>・勤怠修正申請を一覧表示する(UC-207)<br>・シフト日時変更申請を一覧表示する(UC-212) |

## イベントフロー

### メインフロー

1. アクターはシステムに通知の表示を要求する
2. システムはアクターにアクター宛ての通知の一覧(内容、作成日時)を提示する
3. アクターはシステムに一覧から通知を1件指定する
4. システムはアクターに指定された通知の内容を提示する
5. システムはアクターにその通知に関連する対象(シフト、シフト希望、勤怠修正申請、シフト日時変更申請、勤怠記録のいずれか)を提示する

### 代替フロー

#### Alt-1: メインフロー2で、アクター宛ての通知が存在しなかった場合

1. システムはアクター宛ての通知が存在しないことをアクターに提示する
2. このユースケースを終了する

### 例外フロー

なし

## 備考

1. #81で新設した(#81の表現は「通知を確認する」。ADR-0002により「通知を表示する」とした)
2. アクターは従業員と勤怠管理者の両方(#81、#97について2026-10-21の会話で決定)。勤怠管理者もアクター自身の所属単位の従業員として受け取った通知を含め、アクター宛ての通知をすべて提示する
3. 従業員宛ての通知の内容は次のとおり: シフトを公開する(UC-216)でシフトが公開されたこと、シフトを変更する(UC-202)で公開済みのシフトが変更されたこと、シフトを削除する(UC-203)で公開済みのシフトが削除されたこと、シフト希望を承認する(UC-205)の承認結果、シフト希望を却下する(UC-206)の却下結果と却下理由、勤怠修正申請を承認する(UC-208)の承認結果、勤怠修正申請を却下する(UC-209)の却下結果と却下理由、従業員の勤怠を修正する(UC-210)で勤怠記録が修正されたこと、シフト日時変更申請を承認する(UC-213)の承認結果、シフト日時変更申請を却下する(UC-214)の却下結果と却下理由
4. シフト希望を承認する(UC-205)で登録したシフトは状態「公開」で登録され、承認結果の通知が公開の通知を兼ねる。この通知で関連する対象として提示するのは、承認で登録された公開済みのシフト(#87、2026-10-22の会話)
5. 勤怠管理者宛ての通知は、管理先の従業員が勤怠修正申請を送信する(UC-306)・シフト希望を送信する(UC-307)・シフト日時変更申請を送信する(UC-309)で申請・シフト希望を送信したこと(#96)。関連する対象は、勤怠修正申請を一覧表示する(UC-207)・シフト希望を一覧表示する(UC-204)・シフト日時変更申請を一覧表示する(UC-212)で提示される。取り下げは通知されない(2026-10-22の会話)
6. 既読の扱い(表示済みの通知を区別して提示するか)はTBD(要起票)
7. 削除されたシフトの通知で関連する対象として何を提示するかはTBD(要起票)
8. 新設のユースケースであり、IDは仮。requirements.mdのUC一覧にも追記済み
9. 却下結果と却下理由は、通知のほか、シフト希望はシフト希望を一覧表示する(UC-311)、勤怠修正申請は勤怠修正申請内容を一覧表示する(UC-310)、シフト日時変更申請はシフト日時変更申請内容を一覧表示する(UC-318)で提示される(2026-10-22の会話)
