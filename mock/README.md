# Kinchan UCモック(パターンB: ドキュメント忠実)

requirements.md・ADR・UC 詳細ドキュメント(`.ucdocs/`)に**書かれていることだけ**を画面にしたモックです。書かれていない振る舞い・画面・入力項目・文言は補っていません。未定義の箇所は未定義のまま、矛盾している箇所は両方の記述を並べたまま画面に出しています。

同じドキュメントから作ったパターンA(一般的な勤怠アプリの慣行で補ったもの)と見比べ、「どこが決まっていないか」を洗い出すためのものです。成果物の中心は「判断ログ」の章です。

## 起動方法

- `mock/index.html` をブラウザで直接開く(`file://` で動きます)。
- または `cd mock && python3 -m http.server 8000` を実行し、<http://localhost:8000/> を開く。
- ビルド・外部 CDN・バックエンドは不要です(vanilla HTML/CSS/JS)。最新の Chrome / Firefox / Edge を想定しています。

### 前提

- 当月は 2026年10月、今日は **2026-10-14(水)固定**です(時刻だけ実際の時刻を使います)。
- データはページ内のメモリだけに持ち、全ロールで共有します。再読み込みすると初期データに戻ります。
- 従業員の画面はスマホ幅(390px)、管理者・勤怠管理者の画面は PC 幅を前提にしています。

### 画面の見方

| 見た目 | 意味 |
| --- | --- |
| 通常の表示 | ドキュメントに書かれている要素 |
| 破線枠 + `TBD #n` | 未定義・曖昧な要素。中身がない場合は斜線のプレースホルダになる |
| 赤バッジ `矛盾 #n` | ドキュメント間・ドキュメント内で記述が食い違っている箇所 |
| グレーの斜線 + 「モック操作(仕様外)」 | 仕様ではなく、モックを動かすためだけの要素(ナビゲーション、戻るリンク、デモアカウントなど) |
| 斜体の文言 + `TBD #2 文言TBD` | 文言が書かれていないメッセージ。記述の該当句をそのまま出している |

- チップにマウスを乗せると判断ログの要約が、クリックすると全文(曖昧点・採用した扱い・根拠)が出ます。
- 上部バーの「判断ログ」から一覧画面を開けます(README の表と同じ内容)。「注記: 表示/非表示」でチップを隠せます。
- ドキュメントに書かれていないケースに操作が到達した場合は、「この操作の扱いは未定義です」ダイアログを出し、データは変更しません(判断ログ #6)。

### デモ操作パネル(上部バーの「デモ操作」)

- **障害注入**: ドキュメントの例外・代替フロー(通信エラー、処理済み・取り下げ済み、ユーザー0件など)を、次の操作で1回だけ発生させます。
- **シフト希望の受付期間**: 2026年11月分の受付期間の内/外を切り替えます(期間外ではシフト希望提出ボタンが消えます)。
- **イベントログ**: 従業員への通知(方式TBD #5)と履歴の記録(表示UCなし #12)は画面がないため、ここに記録を出します。

### ロールをまたぐデモの例

1. **勤怠修正申請**: 田中(従業員)でログイン → UC-303 ページ →「勤怠記録一覧画面」→ 10/12 の「勤怠修正申請ボタン」→ 送信 → ロール切替で佐藤(勤怠管理者)→ 勤怠修正申請を一覧表示する → 承認 → 田中に戻る →「勤怠修正申請一覧」でステータスが変わっている。
2. **シフト希望**: 田中 →「シフト希望提出」→ 11月分を入力して送信 → 佐藤 → シフト希望を一覧表示する → 時間指定の行を承認 → 田中 →「登録シフト一覧(全体シフト)」で 11月を開くと承認したシフトが出ている(#44)。
3. **シフト日時変更申請**: 田中 → UC-309(TBD ページの導出フォーム)から送信 → 佐藤 → シフト日時変更申請を一覧表示する → 承認/却下(却下理由を従業員が見る画面はない: #70)。

### 判断ログの更新

判断ログの正本は `mock/js/log-data.js` です。編集したら次のコマンドで README の表を作り直してください。

```sh
node mock/tools/gen-readme-log.js
```

## ドキュメントの矛盾・疑問

モックの画面に影響するものは判断ログにも載せ、`(#n)` で対応を示しています。

### 1. UC ID のずれ

管理者の UC 詳細ドキュメント(docx)は古い ID 体系で書かれています。このモックは名前で対応づけ、ID は requirements.md に合わせています。

| --- | --- | --- |
| UC-101 管理者ログイン(表題は「ユーザーを登録する(UC-101)」) | UC-001 ログインする | 表題と内容が食い違っている(内容はログイン) |
| UC-102 管理者ログアウト | UC-002 ログアウトする | |
| UC-103〜UC-107 | UC-103〜UC-107 | 同じ ID |

| UC-110 / UC-111 勤務可能時間 | UC-112 / UC-113 | docx UC-111 は UC-110 をそのまま複製したもので、表題も「勤務可能時間を設定する」(#36) |
| UC-112 / UC-113 休憩時間 | UC-114 / UC-115 | |
| UC-114 ユーザー一覧 | UC-116 | |

- docx の中でも、ID の体系が混ざっています。docx UC-113 の関連UC「休憩時間を設定する(UC-112)」は旧体系の ID です。一方、勤怠管理者 docx UC-203 備考の「UC-114(休憩時間)」「UC-112(勤務可能時間)」は requirements.md の ID です。旧体系で読むと、UC-114 はユーザー一覧、UC-112 は休憩時間を指してしまいます。

### 6. FR と UC の対応のずれ

- FR-003「ユーザー・権限の登録・編集・削除」: 権限の削除にあたる UC がない(UC-106 付与・UC-107 変更のみ)。
- FR-007「シフト作成・割当・変更・削除」: UC 側は「登録」で、「作成」「割当」という語と合わない。割当にあたる UC もない。
- FR-010「勤怠・打刻履歴閲覧」: 関連UC が UC-212(勤怠を**修正**する)と UC-213 になっている。打刻履歴を表示する UC はない。
- FR-012「マイページを表示」: ADR-0003 で TBD 扱い。

### 7. アクター・語彙の不一致

- 従業員 docx の「管理者」が勤怠管理者を指しているように読める(UC-304 備考「管理者の承認」、UC-308 備考「管理者が作成中」、UC-310「管理者からのコメント」)(#10)

- UC-305 Ex-1 が打刻種類とステータス名を取り違えている(#74)

### 8. 1つのドキュメント・関連する UC の中での矛盾

- 打刻種類は2つ(出勤・退勤)なのに、勤務ステータスは3つ(休憩中に移る手段がない)(#72)
- 未登録のユーザーIDが docx UC-101 の Ex-1 と Ex-2 の両方に当てはまる(#20)

- シフト希望の上書き(UC-307)と、日単位の承認(UC-207)の関係(#87)
- UC-306 Ex-2 のフロー本文と事後条件の画面が一致しない(#80)
- 休憩時間の設定・適用・記録・休憩中の関係(#40)
